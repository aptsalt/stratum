How ADK graph workflows work

Stratum is a visual studio for Google ADK 2.x agent graphs. This page is the mental model behind every canvas you build here: what a node is, how layers map to real ADK code, and how a graph goes from a JSON spec on screen to a running, streaming agent.

1. The mental model

ADK 2.x replaced the old hierarchical executor with a graph-based Workflow runtime. The familiar SequentialAgent, ParallelAgent and LoopAgent classes still work, but they are deprecated in favor of describing the same thing as a Workflow of nodes and edges.

A graph is nodes and edges. A node is one of:

  • LlmAgent - a model-backed agent, created with Agent(...).
  • Function - a plain Python function, auto-wrapped as a FunctionNode.
  • Tool - a callable the runtime exposes to an agent.
  • Workflow - a nested graph, used as a single node in a bigger one.
  • JoinNode - waits on multiple predecessors and merges their outputs.
  • RequestInput - a human-input pause point.

Rule of thumb: if a step is deterministic - parsing, formatting, a lookup, a gate condition - write it as a plain function node. It costs no tokens and runs in milliseconds, and it keeps the graph's token-spending surface limited to the steps that actually need a model.

3. From spec to running graph

The canvas you edit is JSON. Stratum validates it, lowers it into ADK's own graph shape, then runs it and streams events back to the same canvas.

The same IR that becomes a live Workflow also emits an exportable agent.py you can run standalone with adk web - the canvas and the CLI run the same graph.

4. Data flow and state

Every node returns an Event with up to four fields, and each one has a different audience:

output

Feeds the next node's node_input.

message

User-facing text only - never read by downstream nodes.

state

Persists in the session, keyed by prefix.

route

Names the branch a router or loop gate should take.

State keys carry a prefix that decides their scope:

app: user: temp: (none)

No prefix means session-scoped state. temp: is scratch space for the current run (like the revision counter in the Loop example above).

Agent instructions can template plain state with {key} and a typed predecessor's field with {Model.field}. Pydantic input_schema / output_schema validate a node's contract at the boundary. On an LlmAgent, output_key saves the reply straight to state, and mode is one of chat, task or single_turn.

5. Graph workflows vs. dynamic workflows

Stratum can compile a spec into either shape. Both run on the same ADK Runner.

Graph mode

Static edges, fully visual, nothing decided at runtime by a model. Because the model never chooses where control flows next, this closes off a whole class of prompt-injection attacks that target routing.

{{ graphModeCode }}
Dynamic mode

One orchestrator function drives everything with ordinary Python - loops, ifs, asyncio.gather for fan-out. ADK checkpoints every ctx.run_node call, so resuming after a pause does not re-run children that already finished.

dynamic_mode.py 
{{ dynamicModeCode }}

Default to graph mode - it is auditable and safe against routing injection. Reach for dynamic mode when the branching genuinely cannot be enumerated up front, or when you need Python-level control (retries, dynamic fan-out width, early exit) that a static edge list cannot express.

6. "Dynamic" means three different things here

It is worth being precise, because the word gets overloaded:

  1. Runtime-composed graphs. Stratum compiles a JSON spec into a live Workflow per request - no redeploy - and specs can be stored per tenant or per user. This is what "editing a graph in Stratum" means.
  2. ADK dynamic workflows. The @node / ctx.run_node pattern from section 5 - control flow expressed as Python inside one node, rather than as edges.
  3. Agent-planned graphs. A planner LLM emits a GraphSpec, which is validated by the exact same rules as a human-edited one before it is compiled. The model proposes structure; it never bypasses validation.

Meaning (c) is a pattern Stratum's architecture enables - the validator does not care who wrote the spec - not a feature that ships today.

7. Human-in-the-loop resume

A gate node does not block a thread - it suspends the run and hands control to the UI.

  1. The node yields RequestInput(message=..., payload=...).
  2. The runner emits a function call named adk_request_input carrying an interrupt id, then stops.
  3. The UI renders an approve / reject card from that payload.
  4. The client sends back a function_response with the same name, the same id, and {"result": "approve"} - under the same invocation_id.
  5. The workflow resumes from where it paused.

If the asking node has rerun_on_resume=False, its output on resume simply becomes the human's answer - it does not execute again.
